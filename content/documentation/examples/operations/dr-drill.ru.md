Резервная копия, которую ни разу не восстанавливали, не гарантирует восстановления. Регулярные учения подтверждают, что снимки пригодны, ключи доступны, процедура описана, а время восстановления укладывается в целевые показатели.

## Цель

Регулярно проверять два сценария восстановления:

- восстановление из снимка Raft в изолированном кластере;
- переключение на DR secondary (Stronghold EE);

и фиксировать фактические время восстановления (RTO) и потерю данных (RPO).

## Периодичность

| Проверка | Периодичность |
| --- | --- |
| `snapshot inspect -validate` для свежего снимка | После каждого снимка или ежедневно |
| Восстановление снимка в изолированном кластере | Раз в квартал и после обновления версии Stronghold |
| Плановое переключение на DR secondary (Stronghold EE) | Раз в полгода |
| Проверка доступности держателей долей ключа распечатывания или восстановления | Раз в квартал |
| Учения по [аварийному доступу](../../access/break-glass-access/) | Раз в полгода |

## Предварительные требования

- Кластер Stronghold со встроенным Raft-хранилищем.
- Изолированный стенд для восстановления: отдельная сеть без доступа к рабочим базам данных, LDAP и другим системам, которыми управляют механизмы секретов.
- Держатели долей ключа распечатывания или восстановления рабочего кластера. После восстановления снимка нужны именно исходные ключи.
- Для второй части — Stronghold EE и настроенная [DR-репликация](../../../admin/replication/disaster-recovery/).

## Часть 1. Восстановление снимка в изолированном кластере

{{< alert level="warning" >}}
Восстановленный кластер содержит рабочие секреты и конфигурацию механизмов секретов. Если он получит сетевой доступ к рабочим системам, он начнёт отзывать просроченные аренды и ротировать пароли в реальных базах данных и LDAP. Изолируйте стенд на сетевом уровне.
{{< /alert >}}

1. Получите снимок. Используйте последний автоматический снимок (Stronghold EE):

   ```bash
   d8 stronghold read sys/storage/raft/snapshot-auto/status/<config_name>
   ```

   Поле `last_snapshot_url` указывает на последний успешный снимок. Либо сохраните снимок вручную:

   ```bash
   d8 stronghold operator raft snapshot save drill.snap
   ```

1. Проверьте целостность снимка:

   ```bash
   d8 stronghold operator raft snapshot inspect -validate drill.snap
   ```

1. Разверните на изолированном стенде кластер Stronghold той же или более новой версии со встроенным Raft-хранилищем (см. [«Установка Stronghold в Linux»](../../../install/standalone/installation/)). Инициализируйте и распечатайте его, войдите временным root-токеном:

   ```bash
   d8 stronghold operator init
   d8 stronghold operator unseal
   d8 stronghold login <temporary_root_token>
   ```

   <!-- TODO(verify): порядок восстановления, если рабочий кластер использует auto-unseal через KMS или встроенный auto-unseal Stronghold EE: нужен ли стенду доступ к тому же KMS -->

1. Зафиксируйте время начала восстановления и восстановите снимок:

   ```bash
   d8 stronghold operator raft snapshot restore -force drill.snap
   ```

1. Распечатайте кластер исходными ключами рабочего кластера:

   ```bash
   d8 stronghold operator unseal
   ```

1. Проверьте данные и зафиксируйте время окончания:

   ```bash
   d8 stronghold status
   d8 stronghold secrets list
   d8 stronghold auth list
   d8 stronghold policy list
   d8 stronghold kv get -mount=secret <known_test_secret>
   ```

   Заранее создайте в рабочем кластере контрольный секрет с меткой времени — по нему удобно определить RPO.

1. Уничтожьте стенд и все копии снимка на нём.

## Часть 2. Плановое переключение на DR secondary

{{< alert level="info" >}}
DR-репликация доступна только в Stronghold EE.
{{< /alert >}}

Проводите переключение в согласованное окно обслуживания. Не повышайте DR secondary, пока primary активен: в кластере окажется два primary.

1. Убедитесь, что secondary догнал primary: значение `last_wal` на secondary равно `last_remote_wal`:

   ```bash
   d8 stronghold read -address="${SECONDARY_ADDR}" sys/replication/dr/status
   ```

1. Понизьте текущий primary:

   ```bash
   d8 stronghold write -address="${PRIMARY_ADDR}" -force sys/replication/dr/primary/demote
   ```

1. Выпустите DR operation token на secondary по процедуре с долями ключей и повысьте secondary. Команды приведены в разделе [«Повышение DR-secondary»](../../../admin/replication/disaster-recovery/#повышение-dr-secondary).

1. Переключите клиентов на новый primary (DNS-запись или балансировщик) и зафиксируйте время.

1. Проверьте работу: вход через OIDC, чтение секретов, выдачу динамических учётных данных и сертификатов.

1. Верните прежний primary в роль secondary. На новом primary выпустите activation-токен и подключите прежний primary:

   ```bash
   d8 stronghold write -address="${SECONDARY_ADDR}" sys/replication/dr/primary/secondary-token id=dr-old-primary
   d8 stronghold write -address="${PRIMARY_ADDR}" sys/replication/dr/secondary/update-primary token=<activation_token>
   ```

1. При необходимости выполните обратное переключение теми же шагами.

## Чек-лист учений

- [ ] Снимок прошёл `inspect -validate`.
- [ ] Держатели долей ключей доступны, кворум собран за приемлемое время.
- [ ] Восстановленный кластер распечатан исходными ключами.
- [ ] Контрольный секрет прочитан, RPO измерено.
- [ ] Методы аутентификации, политики и mount присутствуют в ожидаемом составе.
- [ ] Для DR: secondary повышен, клиенты переключены, прежний primary подключён как secondary.
- [ ] Время восстановления (RTO) измерено и сравнено с целевым.
- [ ] Изолированный стенд и копии снимка уничтожены.
- [ ] Найденные проблемы внесены в регламент восстановления.

## Проверка

Учения считаются успешными, если фактические RTO и RPO не превышают целевых значений, а все пункты чек-листа выполнены. Сохраните протокол учений: дату, участников, версию Stronghold, использованный снимок, измеренные RTO и RPO, выявленные проблемы.

## Очистка

1. Удалите изолированный кластер и его хранилище.
1. Удалите локальные копии снимка: `shred -u drill.snap`.
1. Отзовите токены, выпущенные для учений на рабочем кластере.
