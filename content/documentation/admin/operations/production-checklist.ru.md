Используйте этот чек-лист перед вводом Stronghold в промышленную эксплуатацию и при периодическом аудите конфигурации. Пункты, относящиеся к возможностям Stronghold EE, отмечены отдельно.

## Сеть и TLS

- [ ] TLS включён на всех слушателях. Параметр `tls_disable` не используется (см. [«Настройка»](../../../install/standalone/configuration/#listener)). В DP все сетевые listener'ы используют TLS; только listener метрик `127.0.0.1:8400` внутри Pod'а работает без TLS и недоступен снаружи.
- [ ] Минимальная версия TLS — `tls12` или `tls13` (параметр `tls_min_version`).
- [ ] Для межузлового взаимодействия Raft используются отдельные сертификаты узлов и общий CA.
- [ ] Настроен контроль срока действия сертификатов и процедура их замены (см. [«TLS-сертификаты»](../tls-certificates/)).
- [ ] Доступ к порту API (`8200`) ограничен сетями клиентов, к порту кластера (`8201`) — только узлами Stronghold.
- [ ] В DP порты Pod'а: `8200` (API), `8201` (порт кластера), `8300`/`8301` (внутренние API и порт кластера между Pod'ами), `8500` (mTLS-listener, только при инлетах `Ingress` и `GatewayAPI`) и `9889` (метрики через `kube-rbac-proxy`). Порт `8201` публикуется за пределы кластера только для репликации (`publishCluster`).
- [ ] Доступ к эндпоинтам `sys/metrics` и `sys/pprof` без аутентификации либо отключён, либо ограничен доверенной сетью.
- [ ] При использовании балансировщика или прокси настроены `x_forwarded_for_authorized_addrs` и проверка `sys/health`.

## Доступ и аутентификация

- [ ] Root-токен, полученный при инициализации, отозван после начальной настройки. Для экстренных операций root-токен генерируется заново через `d8 stronghold operator generate-root` (см. [«Управление ключами»](../key-management/#генерация-root-токена)). Это относится к standalone-установке и режиму `Manual` в DP. В режиме `Automatic` в DP секрет `stronghold-keys` содержит `unsealKey` и `rootToken`, а автоконфигуратор `stronghold-automatic` использует root-токен, поэтому отзывать его не нужно. Вместо этого, как рекомендовано для угрозы TM-01 в модели угроз Stronghold, заберите ключи из секрета и храните их в защищённом контуре вне кластера и/или выполните ротацию хранящихся в нём значений, минимизируйте RBAC-доступ к секрету и включите Kubernetes audit.
- [ ] Администраторы входят через внешний провайдер ([OIDC](../../../user/auth/oidc/) или [LDAP](../../../user/auth/ldap/)), а не через [userpass](../../../user/auth/userpass/).
- [ ] Для административных ролей включена [многофакторная аутентификация](../../../user/auth/mfa/totp/).
- [ ] Приложения используют машинные методы аутентификации ([Kubernetes](../../../user/auth/kubernetes/), [AppRole](../../../user/auth/approle/), [JWT](../../../user/auth/jwt/)) без долгоживущих статических токенов.
- [ ] Политики построены по принципу минимальных привилегий, использование `*` и `sudo` ограничено (см. [«Политики»](../../../concepts/policy/)).
- [ ] Политики хранятся в системе контроля версий и применяются автоматически.
- [ ] Настроена блокировка пользователей при подборе пароля (блок [`user_lockout`](../../../install/standalone/configuration/#user_lockout)).

## Аудит

- [ ] Включено не менее двух аудит-устройств (Stronghold EE, см. [«Аудит в Stronghold»](../../audit/overview/)).
- [ ] Журналы аудита отправляются в централизованную систему с ограниченным доступом.
- [ ] Настроены алерты на ошибки записи в аудит-устройства (см. [«Мониторинг»](../monitoring/)).
- [ ] Для устройства `file` настроена ротация журналов и контроль свободного места.

## Время жизни и лимиты

- [ ] Глобальные `default_lease_ttl` и `max_lease_ttl` уменьшены относительно значения по умолчанию (`768h`) до значений, соответствующих политике безопасности.
- [ ] TTL настроены на уровне точек монтирования и ролей методов аутентификации.
- [ ] Настроены [квоты](../quotas/) ограничения частоты запросов для методов аутентификации и нагруженных путей.

## Seal и ключи

- [ ] Используется автоматическое распечатывание через [HSM](../../kms-hsm/hsm/) или [KMS](../../kms-hsm/yandexcloudkms/), либо определён регламент ручного распечатывания с Shamir.
- [ ] Доли ключей распечатывания или восстановления распределены между разными доверенными лицами и зашифрованы их PGP-ключами.
- [ ] Ни у одного лица нет порогового количества долей.
- [ ] Определён регламент хранения ключей (сейф, конверты, журнал выдачи) и замены держателей.
- [ ] Настроена автоматическая ротация ключа шифрования (`sys/rotate/config`, см. [«Управление ключами»](../key-management/#ротация-ключа-шифрования)).

## Резервное копирование

- [ ] Настроено регулярное создание снимков Raft ([вручную](../../backups/save/) или [автоматически](../../backups/automated-snapshots/) в Stronghold EE).
- [ ] Снимки хранятся вне кластера, в хранилище с ограниченным доступом.
- [ ] Регулярно выполняется тестовое [восстановление из снимка](../../backups/restore/) на изолированном стенде.
- [ ] Доли ключей, необходимые для распечатывания восстановленного кластера, доступны отдельно от снимков.

## Операционная система и узлы

- [ ] Используется [поддерживаемая ОС](../../../about/requirements/#поддерживаемые-ос), обновления безопасности устанавливаются регулярно.
- [ ] Stronghold запущен от отдельного непривилегированного пользователя (`stronghold`), каталоги данных имеют права `0700`. В DP Pod работает от non-root пользователя с UID 64535, с корневой файловой системой только для чтения и отброшенными привилегиями (`drop: ALL`).
- [ ] Swap отключён или зашифрован (standalone; в DP модуль задаёт `disable_mlock = true`). При встроенном хранилище Raft рекомендуется `disable_mlock = true` при отключённом swap (см. [«Настройка»](../../../install/standalone/configuration/)).
- [ ] Отключено создание дампов памяти (core dumps) для процесса Stronghold, например `LimitCORE=0` в systemd-unit (standalone).
- [ ] На узлах нет посторонних сервисов, доступ по SSH ограничен и журналируется.
- [ ] Время синхронизировано по NTP на всех узлах.
- [ ] Для данных Raft используется локальный SSD-диск (см. [«Планирование ресурсов»](../sizing/)).

## Высокая доступность

- [ ] Кластер Raft состоит из 3 или 5 узлов, размещённых в разных зонах отказа.

{{< alert level="info" >}}
**В DP** количество реплик равно числу master-узлов плюс arbiter-узлов, округлённому до нечётного (+1, если число чётное). У PodDisruptionBudget `stronghold` значение `minAvailable` равно `replicas/2 + 1` (с округлением вниз). Деструктивные миграции хранилища требуют не менее 3 реплик. См. также [«Планирование ресурсов»](../sizing/#в-dp).
{{< /alert >}}

- [ ] Настроены `retry_join` для всех узлов.
- [ ] Проверена процедура [восстановления после потери кворума](../../../install/standalone/raft-lost-quorum-recovery/).
- [ ] Для катастрофоустойчивости настроена [DR-репликация](../../replication/disaster-recovery/) (Stronghold EE).

## Мониторинг

- [ ] Метрики собираются со всех узлов, настроены алерты из раздела [«Мониторинг»](../monitoring/).
- [ ] Балансировщик и внешний мониторинг используют `sys/health`.
- [ ] [Серверные журналы](../logs/) собираются в централизованную систему.
- [ ] Описана и проверена процедура [обновления](../../../install/standalone/update/).
