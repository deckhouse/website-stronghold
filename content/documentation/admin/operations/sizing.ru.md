Профиль нагрузки на хранилище секретов сильно различается между организациями, поэтому приведённые значения следует рассматривать как отправную точку. Проверяйте фактическое потребление ресурсов по метрикам (см. [«Мониторинг»](../monitoring/)) и корректируйте размер кластера.

Базовые системные требования приведены в разделе [«Требования»](../../../about/requirements/).

## Профили кластера

Значения для небольшого и большого кластера взяты из раздела [«Требования»](../../../about/requirements/). Профиль «Средний» и объём диска — рекомендации, которые нужно проверить на своей нагрузке.

| Параметр | Небольшой | Средний (рекомендация) | Большой |
| --- | --- | --- | --- |
| Назначение | Разработка, тестирование, начальные развёртывания | Production с умеренной нагрузкой | Production с постоянной высокой нагрузкой |
| Процессор | 4–8 ядер | 8 ядер | 8–16 ядер |

| Операции дискового ввода-вывода | 3000+ оп/с | 3000+ оп/с | 3000+ оп/с |
| Пропускная способность диска | 70+ МБ/с | 100+ МБ/с | 200+ МБ/с |
| Объём диска для данных Raft | 25 ГБ | 50 ГБ | 100+ ГБ |

## Диск для Raft

Каждая запись в Stronghold фиксируется в журнале Raft на большинстве узлов с синхронизацией на диск, поэтому задержка диска напрямую влияет на время записи и стабильность выборов лидера.

Рекомендации:

- используйте локальные SSD или NVMe-диски; избегайте сетевых дисков с непредсказуемой задержкой;
- выделите для данных Raft отдельный раздел, чтобы журналы ОС и аудита не могли заполнить его;
- контролируйте задержку синхронизации на диск — ориентир не более единиц миллисекунд;
- учитывайте, что размер хранилища растёт вместе с количеством аренд и токенов, а снимки Raft требуют места для временных файлов.

Проверить задержку синхронизации диска можно утилитой `fio`:

```shell
fio --name=raft-fsync --directory=/opt/stronghold/data --rw=write \
  --ioengine=sync --fdatasync=1 --bs=4k --size=100m
```

В выводе обратите внимание на перцентили `fsync/fdatasync/sync_file_range`. Удалите созданный тестовый файл после проверки.

## Количество узлов

| Узлов | Допустимо потерять | Когда использовать |
| --- | --- | --- |
| 1 | 0 | Только разработка и тестирование |
| 3 | 1 | Стандартный production-кластер |
| 5 | 2 | Повышенные требования к доступности, размещение в трёх зонах отказа |

Рекомендации:

- используйте нечётное число голосующих узлов: при чётном числе устойчивость к отказам не увеличивается;
- не увеличивайте кластер больше пяти голосующих узлов: каждый дополнительный узел увеличивает время фиксации записи;
- размещайте узлы в разных зонах отказа с низкой сетевой задержкой между ними;
- для горизонтального масштабирования операций чтения используйте [performance standby](../../replication/performance-standby/) (Stronghold EE), для катастрофоустойчивости — [DR-репликацию](../../replication/disaster-recovery/).

## В DP

{{< alert level="info" >}}
- Requests Pod'а `stronghold` — `50m` CPU и `256Mi` памяти; VerticalPodAutoscaler (режим `Initial`) может увеличить их до `500m` и `1Gi`. Pod `stronghold-automatic` запрашивает `10m` CPU и `50Mi` памяти.
- Размер диска по умолчанию (`diskSizeGigabytes`) — 1 ГБ; задайте значение, достаточное для ваших данных.
- Количество реплик равно числу master-узлов плюс arbiter-узлов; если получилось чётное число, добавляется ещё одна реплика.
- У PodDisruptionBudget значение `minAvailable` равно `replicas/2 + 1` (с округлением вниз).
- Деструктивные миграции хранилища требуют не менее 3 реплик.
{{< /alert >}}

## Что создаёт нагрузку

| Фактор | Влияние | Как снизить |
| --- | --- | --- |
| Аренды | Каждая аренда хранится в хранилище и обрабатывается при истечении. Большое количество увеличивает потребление памяти, время запуска и смены лидера | Уменьшайте TTL, отзывайте неиспользуемые аренды, применяйте [квоты](../quotas/) |
| Токены | Каждый вход создаёт токен и запись в хранилище | Переиспользуйте токены, используйте [Stronghold Agent](../../../user/agent/overview/), уменьшайте TTL |
| Аутентификация | Операции входа значительно дороже чтения секрета | Кешируйте токены на стороне клиента |
| Запись | Каждая запись реплицируется через Raft с синхронизацией на диск | Используйте быстрые диски, избегайте частой перезаписи одних и тех же секретов |
| Аудит | Каждый запрос и ответ записываются во все аудит-устройства | Используйте быстрые локальные диски или надёжные сетевые приёмники, [фильтрацию](../../audit/filtering/) |
| Криптографические операции | Механизмы [Transit](../../../user/secrets-engines/transit/) и [PKI](../../../user/secrets-engines/pki/) нагружают CPU, особенно RSA-ключи большой длины | Увеличьте число ядер, выбирайте алгоритмы с меньшей стоимостью |

## Пересмотр размера кластера

Увеличьте ресурсы, если:

- 99-й перцентиль `stronghold_core_handle_request` устойчиво растёт;
- загрузка CPU на активном узле регулярно превышает 70–80%;
- потребление памяти приближается к объёму ОЗУ узла;
- возрастает `stronghold_raft_commitTime` и учащаются выборы лидера.
