API Proxy позволяет Stronghold Agent работать как локальный прокси для API Stronghold.
В этом режиме приложение обращается к локальному эндпоинту Agent,
а Agent добавляет токен аутентификации и проксирует запрос к серверу Stronghold.

На этой странице описано,
как работает API Proxy,
в каких случаях его использовать
и как настроить Stronghold Agent для работы в этом режиме.

## Когда использовать API Proxy

Используйте API Proxy в следующих случаях:

- Приложение уже умеет работать с API Stronghold.
- Нужно передавать токен аутентификации централизованно.
- Нужно уменьшить число прямых подключений к серверу Stronghold.
- Требуется предоставить приложению локальный HTTP(S)-эндпоинт для доступа к Stronghold.

Если приложению нужны секреты в файлах,
используйте режим `template`.
Если приложению нужны секреты в переменных окружения,
используйте `env_template` вместе с `exec`.

## Как работает API Proxy

Обычно Stronghold Agent выполняет следующие действия:

1. Проходит аутентификацию в Stronghold.
1. Запускает локальный listener.
1. Принимает запросы от приложения на локальном адресе.
1. Добавляет токен аутентификации к исходящему запросу.
1. Проксирует запрос к серверу Stronghold.
1. Возвращает ответ приложению.

Такой режим позволяет приложению работать через локальный эндпоинт
вместо прямого подключения к Stronghold.

## Базовая конфигурация

Ниже приведён пример минимальной конфигурации API Proxy:

```hcl
stronghold {
  address = "https://stronghold.example.com:8200"
}

auto_auth {
  method "approle" {
    mount_path = "auth/approle"
    config = {
      role_id_file_path = "/etc/stronghold-agent/role-id"
      secret_id_file_path = "/etc/stronghold-agent/secret-id"
    }
  }
}

api_proxy {
  use_auto_auth_token = true
}

listener "tcp" {
  address = "127.0.0.1:8200"
  tls_disable = true
}
```

В этом примере Agent:

- проходит аутентификацию через AppRole;
- запускает локальный listener на адресе `127.0.0.1:8200`;
- использует токен,
  полученный через Auto-Auth;
- проксирует запросы приложения к серверу Stronghold.

## Как приложение использует локальный эндпоинт

После запуска Agent приложение может обращаться к локальному API Proxy,
например так:

```shell
curl http://127.0.0.1:8200/v1/secret/data/myapp
```

В этом случае приложение отправляет запрос не напрямую в Stronghold,
а на локальный адрес Agent.

## Параметры конфигурации

Для режима API Proxy чаще всего используются следующие блоки:

| Блок или параметр | Описание |
| --- | --- |
| `api_proxy.use_auto_auth_token` | Использует токен, полученный через Auto-Auth |
| `listener "tcp"` | Настраивает локальный listener |
| `listener.address` | Задаёт адрес и порт локального эндпоинта |
| `listener.tls_disable` | Отключает TLS на локальном listener |

## Ограничения и особенности

Учитывайте следующие особенности режима API Proxy:

- Приложение должно уметь работать с API Stronghold.
- Безопасность локального listener зависит от выбранного адреса и настроек TLS.
- Если listener слушает только `127.0.0.1`,
  доступ к нему ограничен локальной машиной.
- Режим API Proxy не предназначен для передачи секретов через переменные окружения или файлы.
- Не комбинируйте `api_proxy` с `env_template` в одном конфигурационном файле.

{{< alert level="warning" >}}
Если вы отключаете TLS на локальном listener,
используйте адрес,
доступный только локально,
например `127.0.0.1`.
{{< /alert >}}

## Проверка

После настройки API Proxy выполните следующие действия:

1. Запустите Stronghold Agent.
1. Убедитесь,
   что локальный listener доступен.
1. Выполните тестовый запрос к локальному эндпоинту.
1. Проверьте,
   что запрос успешно проксируется в Stronghold.

Пример проверки:

```shell
systemctl start stronghold-agent
journalctl -u stronghold-agent -n 50
curl http://127.0.0.1:8200/v1/secret/data/myapp
```
