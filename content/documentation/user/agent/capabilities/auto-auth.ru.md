Auto-Auth автоматизирует получение токена для работы Stronghold Agent.
Агент самостоятельно проходит аутентификацию в Stronghold,
получает токен и использует его для запросов к API Stronghold.

На этой странице описано,
как работает Auto-Auth,
какие задачи он решает
и какие методы аутентификации поддерживает Stronghold Agent.

## Как работает Auto-Auth

Auto-Auth выполняет следующие задачи:

- Проходит аутентификацию в Stronghold без участия приложения.
- Получает токен и передаёт его внутренним подсистемам Agent.
- При необходимости записывает токен во внешний sink.
- Обновляет токен до истечения срока действия.
- Повторно проходит аутентификацию,
  если токен больше нельзя обновить.

Обычно последовательность работы выглядит так:

1. Stronghold Agent запускается с настроенным методом аутентификации.
1. Агент проходит аутентификацию в Stronghold.
1. Агент получает токен.
1. Агент использует токен для рендеринга шаблонов,
   Process Supervisor или API Proxy.
1. Если настроен sink,
   Agent записывает токен во внешний файл.
1. Агент обновляет токен до истечения TTL.
1. Если обновление недоступно,
   Agent проходит аутентификацию повторно.

## Зачем использовать Auto-Auth

Auto-Auth полезен в следующих случаях:

- Приложение не должно самостоятельно работать с механизмами аутентификации.
- Нужно автоматически получать токен после запуска Agent.
- Нужно поддерживать длительную работу приложения без ручного обновления токена.
- Один и тот же токен должен использоваться в нескольких режимах Agent.

## Sink

Sink — это место,
куда Stronghold Agent записывает полученный токен.

Если sink настроен,
токен можно использовать во внешнем процессе.
Например,
его можно записать в файл `/var/run/stronghold-agent/token`.

Если sink не настроен,
токен используется только внутри самого Agent.

Пример настройки sink:

```hcl
auto_auth {
  method "approle" {
    mount_path = "auth/approle"
    config = {
      role_id_file_path = "/etc/stronghold-agent/role-id"
      secret_id_file_path = "/etc/stronghold-agent/secret-id"
    }
  }

  sink "file" {
    config = {
      path = "/var/run/stronghold-agent/token"
      mode = 0640
    }
  }
}
```

## Поддерживаемые методы аутентификации

Stronghold Agent поддерживает следующие методы аутентификации:

| Метод | Когда использовать | Подробности |
| --- | --- | --- |
| AppRole | Для приложений на виртуальных машинах и bare metal | [AppRole](../auth-approle/) |
| Token | Для простых или временных сценариев | [Аутентификация по токену](../auth-token/) |
| JWT/OIDC | Для интеграции с внешним провайдером идентификации | [JWT/OIDC](../auth-jwt-oidc/) |
| Методы облачных провайдеров | Для сред, где доступен нативный механизм аутентификации | — |

## Обновление токена

Если Stronghold Agent получает токен с ограниченным TTL,
он старается обновить его заранее.

Это позволяет:

- уменьшить число повторных аутентификаций;
- снизить нагрузку на сервер Stronghold;
- поддерживать непрерывную работу приложения.

Если токен нельзя обновить,
Agent повторно проходит аутентификацию
и получает новый токен.

## Обновление динамических секретов

Auto-Auth связан не только с получением токена,
но и с непрерывной работой Agent в целом.
Если Agent использует динамические credentials,
он может обновлять их до завершения срока действия.

Это особенно важно в следующих случаях:

- используются временные credentials базы данных;
- используются сертификаты с ограниченным временем жизни;
- приложение работает долго и не должно терять доступ к секретам.

После обновления секрета Agent может:

- повторно рендерить файл;
- перезапускать дочерний процесс;
- продолжать проксирование запросов с актуальным токеном.

## Пример базовой конфигурации

Ниже приведён пример минимальной конфигурации Auto-Auth с методом AppRole
и файловым sink:

```hcl
stronghold {
  address = "https://stronghold.example.com:8200"
}

auto_auth {
  method "approle" {
    mount_path = "auth/approle"
    config = {
      role_id_file_path = "/etc/stronghold-agent/role-id"
      secret_id_file_path = "/etc/stronghold-agent/secret-id"
      remove_secret_id_file_after_reading = true
    }
  }

  sink "file" {
    config = {
      path = "/var/run/stronghold-agent/token"
      mode = 0640
    }
  }
}
```

## Как выбрать метод аутентификации

Выбирайте метод аутентификации в зависимости от среды выполнения и требований безопасности:

- Используйте AppRole для виртуальных машин и bare metal.
- Используйте token только для простых, тестовых или временных сценариев.
- Используйте JWT/OIDC,
  если нужно интегрироваться с внешним провайдером идентификации.
- Используйте механизм облачного провайдера,
  если Stronghold развёрнут в соответствующей облачной среде.

## Ограничения и особенности

Учитывайте следующие особенности Auto-Auth:

- Auto-Auth отвечает только за получение и обновление токена.
- Конкретные требования зависят от выбранного метода аутентификации.
- Не все методы одинаково подходят для production-окружения.
- Если токен записывается во внешний файл,
  ограничьте права доступа к этому файлу.

{{< alert level="info" >}}
Если вы выбираете метод аутентификации для production-окружения,
обычно рекомендуется использовать AppRole для виртуальных машин и bare metal
или JWT/OIDC для интеграции с внешним провайдером идентификации.
{{< /alert >}}
