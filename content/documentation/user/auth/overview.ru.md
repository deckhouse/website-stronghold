**Методы аутентификации в Deckhouse Stronghold** определяют, как пользователь, приложение или сервис подтверждает свою личность и получает доступ к хранилищу секретов. После успешной аутентификации Deckhouse Stronghold выдаёт токен, с которым клиент выполняет дальнейшие запросы.

Deckhouse Stronghold поддерживает несколько методов аутентификации одновременно. Это позволяет использовать разные сценарии доступа в одной инсталляции: вход пользователей через браузер или CLI, аутентификацию приложений и сервисов, интеграцию с корпоративными каталогами и применение дополнительных факторов защиты.

При выборе метода аутентификации учитывайте не только способ входа, но и то, кто именно получает доступ к Deckhouse Stronghold:

- пользователь;
- приложение;
- сервис;
- приложение в Kubernetes;
- внешний инструмент или интеграция.

{{< alert level="info" >}}
Конкретный метод аутентификации должен быть заранее включён и настроен администратором. Если нужный метод недоступен в вашей инсталляции, обратитесь к администратору Deckhouse Stronghold.
{{< /alert >}}

## Как выбрать подходящий метод

В общем случае методы аутентификации можно разделить на три группы:

- **пользовательские методы** — для входа человека через браузер, CLI или веб-интерфейс;
- **машинные методы** — для приложений, сервисов и автоматизации;
- **дополнительные факторы защиты** — для усиления уже существующей схемы входа.

Если вы не уверены, какой вариант использовать, ориентируйтесь на следующий подход:

- если вы входите как пользователь через браузер или корпоративную учётную запись, обычно подходит [`OIDC`](./oidc/overview), [`SAML`](./saml), [`LDAP`](./ldap), [`Userpass`](./userpass) или [`WebAuthn`](./web-auth-n);
- если доступ нужен приложению или сервису, чаще используют [`AppRole`](./approle), [`Kubernetes`](./kubernetes), [`JWT`](./jwt) или [`Token`](./token);
- если для входа требуется дополнительное подтверждение, используйте [`MFA`](#mfa).

## Методы для пользователей

### OIDC

[OpenID Connect (OIDC)](./oidc/overview) — один из основных методов входа для пользователей. Он позволяет аутентифицироваться через внешний OIDC-провайдер с помощью браузера и поддерживает сценарии для UI и CLI.

Этот метод обычно выбирают в следующих случаях:

- в организации уже есть OIDC-провайдер;
- нужен единый вход через корпоративную учётную запись;
- требуется удобный пользовательский сценарий для браузера и CLI.

Если вам нужно понять, как Deckhouse Stronghold работает с конкретными OIDC-провайдерами, используйте раздел [Провайдеры OIDC](./oidc/oidc-providers/overview).

### SAML

[Security Assertion Markup Language (SAML)](./saml) позволяет аутентифицировать пользователей через внешний `SAML 2.0` identity-провайдер по профилю `Web SSO`.

Этот метод подходит в следующих случаях:

- в организации уже используется SAML-инфраструктура;
- нужен браузерный вход через корпоративный identity-провайдер;
- требуется интеграция с системами, ориентированными на SAML.

### LDAP

[Lightweight Directory Access Protocol (LDAP)](./ldap) используется для аутентификации через существующий LDAP-каталог или Active Directory.

Этот метод подходит в следующих случаях:

- учётные записи пользователей уже ведутся в LDAP;
- нужно связать пользователей и группы каталога с политиками Deckhouse Stronghold;
- требуется интеграция с корпоративной службой каталогов.

### Userpass

[`Userpass`](./userpass) — встроенный метод аутентификации по имени пользователя и паролю.

Он подходит в следующих случаях:

- требуется простой локальный способ входа;
- не используется внешний identity-провайдер;
- нужен базовый сценарий аутентификации для тестирования, внутренних стендов или ограниченного числа пользователей.

### WebAuthn

[`WebAuthn`](./web-auth-n) позволяет аутентифицироваться с помощью `FIDO2`-совместимых аутентификаторов и `passkeys`.

Этот метод особенно полезен в следующих случаях:

- нужен беспарольный вход;
- требуется современный браузерный пользовательский сценарий;
- нужно усилить защиту учётных записей за счёт аппаратного или платформенного аутентификатора.

### Token

[`Token`](./token) — встроенный метод аутентификации по токену. Он автоматически доступен в Deckhouse Stronghold и может использоваться как пользователями, так и средствами автоматизации.

Этот метод обычно применяют в следующих случаях:

- у пользователя уже есть действующий токен;
- требуется выполнить вход без повторной аутентификации через внешний метод;
- используется сценарий автоматизации или прямой работы с API Deckhouse Stronghold.

## Методы для приложений и сервисов

### AppRole

[`AppRole`](./approle) предназначен для аутентификации приложений и сервисов. Он особенно хорошо подходит для машинных сценариев, когда нужно выдать приложению доступ на основе роли и дополнительных ограничений.

Этот метод обычно выбирают в следующих случаях:

- доступ нужен приложению, а не человеку;
- требуется гибкий и управляемый сценарий аутентификации сервисов;
- необходимо разделить доставку `role_id` и `secret_id`;
- используется автоматизация или взаимодействие между сервисами.

### JWT

[JSON Web Token (JWT)](./jwt) используется, когда клиент уже может предоставить готовый JWT, который Deckhouse Stronghold должен проверить.

Этот метод подходит в следующих случаях:

- приложение уже получает JWT от доверенного issuer;
- требуется аутентификация без браузерного OIDC-сценария;
- нужно использовать проверки claims и привязки по утверждениям токена.

### Kubernetes

[`Kubernetes`](./kubernetes) предназначен для аутентификации приложений в Kubernetes с помощью токена `ServiceAccount`.

Этот метод особенно полезен в следующих случаях:

- приложение работает в Kubernetes;
- Deckhouse Stronghold используется для доставки секретов в поды;
- нужно выдавать токены Deckhouse Stronghold на основе identity Kubernetes.

## Дополнительный уровень защиты

### MFA

[Multi-Factor Authentication (MFA)](./mfa) — это не отдельный базовый способ входа, а дополнительный фактор проверки, который усиливает уже настроенный метод аутентификации.

Deckhouse Stronghold поддерживает разные сценарии MFA, в том числе:

- [`MULTIFACTOR Ldap Adapter`](./mfa/mfla) — для двухфакторной защиты пользователей в LDAP-сценариях;
- [`Time-Based One-Time Password (TOTP)`](./mfa/totp) — для проверки одноразовых кодов.

MFA стоит использовать в следующих случаях:

- требуется усилить защиту пользовательского входа;
- организация предъявляет повышенные требования к безопасности;
- необходимо добавить второй фактор для методов вроде LDAP, Userpass или других пользовательских сценариев.

## Что выбрать в типовых сценариях

Ниже приведены упрощённые рекомендации:

- Для входа пользователя через корпоративную учётную запись обычно подходят [`OIDC`](./oidc/overview) или [`SAML`](./saml).
- Для входа пользователя через LDAP или Active Directory подходит [`LDAP`](./ldap).
- Для простого локального входа по логину и паролю подходит [`Userpass`](./userpass).
- Для беспарольного входа подходит [`WebAuthn`](./web-auth-n).
- Для аутентификации приложения или сервиса подходит [`AppRole`](./approle).
- Для аутентификации приложения в Kubernetes подходит [`Kubernetes`](./kubernetes).
- Для аутентификации по уже выданному JWT подходит [`JWT`](./jwt).
- Для работы с уже существующим токеном Deckhouse Stronghold подходит [`Token`](./token).
- Для усиления существующей схемы входа подходит [`MFA`](./mfa).

## Особенности внешних методов аутентификации

Во многих сценариях Deckhouse Stronghold делегирует аутентификацию внешнему методу, например `JWT`, `OIDC`, `Kubernetes` или `LDAP`. В качестве источника данных о пользователях и приложениях при этом могут использоваться внешние системы, например Deckhouse Kubernetes Platform, Keycloak, Blitz Identity Provider или Active Directory.

При использовании внешнего метода аутентификации Deckhouse Stronghold обращается к внешнему сервису во время входа и при последующих продлениях токена. Если статус сущности изменится во внешней системе, например если учётная запись будет отключена или срок её действия истечёт, Deckhouse Stronghold отклонит запросы на продление токенов, связанных с этой сущностью. При этом уже выданные токены останутся действительными до окончания исходного срока действия, если они не были явно отозваны в Deckhouse Stronghold.

{{< alert level="warning" >}}
При использовании внешних методов аутентификации задавайте подходящий TTL для токенов. Это помогает ограничить срок действия уже выданных токенов, если доступ во внешней системе был изменён или отозван.
{{< /alert >}}

При отключении метода аутентификации все пользователи и приложения, которые аутентифицировались с его помощью, автоматически потеряют возможность выполнять новый вход в систему.
