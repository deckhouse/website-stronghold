Метод `jwt auth` можно использовать для аутентификации в Stronghold двумя способами:
- через OIDC;
- путём прямого предоставления JWT.

В этом разделе рассматривается сценарий OIDC, в котором пользователь проходит аутентификацию через внешний OIDC-провайдер с помощью веб-интерфейса или CLI. Конкретный сценарий зависит от настройки роли.

{{< alert level="info" >}}
Если нужен сценарий, в котором клиент напрямую предоставляет JWT без входа через браузер, используйте раздел [JWT](../../jwt/). В JWT-сценарии Stronghold криптографически проверяет предоставленный токен с помощью локально заданных ключей или ключей, полученных через OIDC Discovery.
{{< /alert >}}

## Как работает OIDC в Stronghold

Сценарий OIDC-аутентификации в Stronghold основан на стандартном входе через браузер. Stronghold перенаправляет пользователя к настроенному OIDC-провайдеру, получает результат аутентификации и выдаёт собственный токен.

Для OIDC Stronghold использует сценарий Authorization Code с расширением PKCE.

Stronghold поддерживает два встроенных сценария OIDC-аутентификации:

- вход через веб-интерфейс Stronghold;
- вход через CLI с помощью команды `d8 stronghold login`.

## Настройка redirect URI

**Корректная настройка redirect URI — одна из самых важных частей настройки OIDC.**

Redirect URI должен:
- быть задан в Stronghold в параметре роли `allowed_redirect_uris`;
- быть настроен у внешнего OIDC-провайдера;
- полностью совпадать в обеих системах.

При проверке совпадения учитывайте:
- протокол — `http` или `https`;
- хост — `127.0.0.1` или `localhost`;
- номер порта;
- наличие или отсутствие завершающего слеша.

## OIDC для CLI

Если планируется вход через CLI с помощью следующей команды:

```shell
d8 stronghold login -method=oidc
```

разрешите redirect URI на `localhost`.

Типовой пример:

```text
http://localhost:8250/oidc/callback
```

Если при входе через CLI используется другой хост или порт, этот URI тоже должен совпадать с одним из значений в `allowed_redirect_uris` и быть разрешён у OIDC-провайдера.

### Вход через CLI

По умолчанию для CLI используется путь `/oidc_deckhouse`. Если метод аутентификации включён по другому пути, укажите его явно:

```shell
d8 stronghold login -method=oidc -path=oidc_deckhouse role=test
```

Пример поведения CLI:

```text
Complete the login via your OIDC provider. Launching browser to:
https://myco.auth0.com/authorize?redirect_uri=http%3A%2F%2Flocalhost%3A8400%2Foidc%2Fcallback&client_id=r3qXc2bix9eF...
```

После этого браузер откроет страницу OIDC-провайдера для завершения входа. Если браузер нельзя открыть автоматически, откройте URL вручную или используйте параметр `skip_browser`.

### Полезные параметры CLI

Для сценария входа через CLI можно использовать следующие параметры:

- `mount` — по умолчанию `oidc`;
- `listenaddress` — по умолчанию `localhost`;
- `port` — по умолчанию `8250`;
- `callbackhost` — по умолчанию `localhost`;
- `callbackmethod` — по умолчанию `http`;
- `callbackport` — по умолчанию совпадает со значением `port`;
- `skip_browser` — по умолчанию `false`.

Обычно изменять эти параметры не требуется. В некоторых сценариях значения `callbackport` и `port` могут различаться: `callbackport` используется в параметре `redirect_uri`, а `port` — для локального сервера, который принимает входящий запрос.

## OIDC для веб-интерфейса

Веб-интерфейс Stronghold поддерживает вход через OIDC напрямую и не требует отдельной настройки. После включения метода аутентификации интерфейс автоматически использует доступный сценарий входа.

### Вход через веб-интерфейс

Типовой пользовательский сценарий:

1. Выберите метод входа OIDC.
1. При необходимости введите имя роли.
1. Нажмите кнопку входа через OIDC-провайдера.
1. Завершите аутентификацию у настроенного провайдера.

## Что настраивается в роли OIDC

Роль OIDC определяет, как Stronghold будет обрабатывать результат аутентификации.

Обратите внимание на следующие параметры:

- `allowed_redirect_uris` задаёт допустимые redirect URI;
- `user_claim` — обязательный и ключевой параметр роли;
- `oidc_scopes` задаёт список scopes, которые Stronghold запрашивает у провайдера;
- при необходимости можно использовать дополнительные привязки claims, например `bound_claims`.

Параметр `bound_audiences` для OIDC-ролей обычно не требуется. Как правило, OIDC-провайдер использует `client_id` для определения аудитории, и стандартной проверки достаточно.

Если параметр роли требует карту значений, задавайте её целиком как JSON-объект, а не конфигурируйте по частям.

Пример:

```shell
d8 stronghold write auth/oidc/role/demo -<<EOF
{
  "user_claim": "sub",
  "bound_audiences": "abc123",
  "role_type": "oidc",
  "policies": "demo",
  "ttl": "1h",
  "bound_claims": { "groups": ["mygroup/mysubgroup"] }
}
EOF
```

## Практические рекомендации по настройке

При настройке OIDC придерживайтесь следующего порядка:

- сначала добейтесь успешного базового входа;
- затем добавляйте ограничения по claims и дополнительные проверки;
- отдельно сверяйте redirect URI в Stronghold и у провайдера;
- запрашивайте у провайдера только действительно нужные scopes.

Например, если Stronghold должен получать профиль пользователя и сведения о его группах, укажите для роли:

```text
oidc_scopes="profile,groups"
```

## Отладка OIDC

Если аутентификация через OIDC не работает, сначала:

- проверьте журналы Stronghold;
- убедитесь, что redirect URI совпадают в Stronghold и у провайдера;
- проверьте, что `user_claim` настроен корректно;
- временно не усложняйте роль дополнительными `bound_claims`;
- уточните у провайдера структуру claims, которые реально приходят в токене.

Если нужно вручную посмотреть содержимое JWT, можно декодировать payload токена.

Например:

```shell
cat jwt.json | jq -r .access_token | cut -d. -f2 | base64 -D
```

Это полезно для диагностики claims и сопоставления их с ожидаемой конфигурацией роли.

## verbose_oidc_logging

В Stronghold доступна ролевая опция `verbose_oidc_logging`.

Если она включена и журналирование работает на уровне `debug`, Stronghold будет записывать полученный OIDC-токен в журналы сервера.

{{< alert level="warning" >}}
Не используйте `verbose_oidc_logging` в production-окружении. Claims могут содержать чувствительные данные.
{{< /alert >}}
