The Kubernetes Secrets Engine for Stronghold generates tokens for Kubernetes ServiceAccounts.
If needed, it can also create ServiceAccount, Role, and RoleBinding objects.
Generated tokens have a configurable time to live (TTL), and all created objects are automatically deleted when the Stronghold [lease](../../concepts/lease/) expires.

For each lease, Stronghold creates a token for a specific ServiceAccount and returns it to the caller.
For more information, see the official Kubernetes documentation on [service accounts](https://kubernetes.io/docs/concepts/security/service-accounts/) and [RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/).

{{< alert level="warning" >}}
Do not use tokens generated by the Kubernetes secrets engine to authenticate with the [Kubernetes Auth Method](../../auth/kubernetes/).
This creates many unique identifiers in Stronghold that are difficult to manage.
{{< /alert >}}

## Configuration

Before using the Kubernetes secrets engine, configure it first.
These steps are usually performed by a Stronghold administrator or a configuration management system.

By default, Stronghold connects to Kubernetes using its own ServiceAccount.
When you use the [Helm chart](https://github.com/hashicorp/vault-helm), this ServiceAccount is created automatically and is named after the Helm release.
By default, its name is `stronghold`, but you can change it with the `server.serviceAccount.name` Helm value.

Make sure the ServiceAccount used by Stronghold has the following permissions:
- To manage ServiceAccount tokens.
- To manage ServiceAccount, Role, and RoleBinding objects if you use automatic object creation.

Manage these permissions with Kubernetes roles.
Bind the role to the Stronghold ServiceAccount by using a ClusterRoleBinding or RoleBinding.

The following example shows a ClusterRole that only allows creating ServiceAccount tokens:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: k8s-minimal-secrets-abilities
rules:
  - apiGroups: [""]
    resources: ["serviceaccounts/token"]
    verbs: ["create"]
```

You can also create a ClusterRole with broader permissions.
The following example grants permissions to manage tokens, ServiceAccounts, RoleBindings, and Roles:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: k8s-full-secrets-abilities
rules:
  - apiGroups: [""]
    resources: ["serviceaccounts", "serviceaccounts/token"]
    verbs: ["create", "update", "delete"]
  - apiGroups: ["rbac.authorization.k8s.io"]
    resources: ["rolebindings", "clusterrolebindings"]
    verbs: ["create", "update", "delete"]
  - apiGroups: ["rbac.authorization.k8s.io"]
    resources: ["roles", "clusterroles"]
    verbs: ["bind", "escalate", "create", "update", "delete"]
```

Create this role in Kubernetes.
For example, use the `d8 k apply -f` command.

If you want to restrict namespace selection by label, grant Stronghold permission to read Namespaces:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: k8s-full-secrets-abilities-with-labels
rules:
  - apiGroups: [""]
    resources: ["namespaces"]
    verbs: ["get"]
  - apiGroups: [""]
    resources: ["serviceaccounts", "serviceaccounts/token"]
    verbs: ["create", "update", "delete"]
  - apiGroups: ["rbac.authorization.k8s.io"]
    resources: ["rolebindings", "clusterrolebindings"]
    verbs: ["create", "update", "delete"]
  - apiGroups: ["rbac.authorization.k8s.io"]
    resources: ["roles", "clusterroles"]
    verbs: ["bind", "escalate", "create", "update", "delete"]
```

{{< alert level="warning" >}}
Finding the correct permissions for Stronghold may require several attempts.
Kubernetes strictly prevents privilege escalation.
For details, see the [Kubernetes RBAC documentation](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#privilege-escalation-prevention-and-bootstrapping).
{{< /alert >}}

{{< alert level="warning" >}}
Protect the Stronghold ServiceAccount, especially if it has broad permissions.
In practice, such an account has administrative access to the cluster.
{{< /alert >}}

Create a role binding to associate the role with the Stronghold ServiceAccount and grant permission to manage tokens:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: stronghold-token-creator-binding
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: k8s-minimal-secrets-abilities
subjects:
  - kind: ServiceAccount
    name: stronghold
    namespace: stronghold
```

For more information about Kubernetes roles, ServiceAccounts, bindings, and tokens, see the [Kubernetes RBAC documentation](https://kubernetes.io/docs/reference/access-authn-authz/rbac/).

If Stronghold will not automatically manage roles or ServiceAccounts, see [Automatic management of roles and ServiceAccounts](#roles-and-sa).
In this case, configure the ServiceAccount for which Stronghold will issue tokens in advance.

{{< alert level="warning" >}}
Use different ServiceAccounts for Stronghold itself and for issuing tokens.
Do not use the same ServiceAccount for both purposes.
{{< /alert >}}

The examples below use the `test` Namespace.
Create it if it does not already exist:

```shell
d8 k create namespace test
```

The following example shows a simple configuration of a ServiceAccount, Role, and RoleBinding in the `test` Namespace with basic permissions:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: test-service-account-with-generated-token
  namespace: test
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: test-role-list-pods
  namespace: test
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: test-role-abilities
  namespace: test
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: test-role-list-pods
subjects:
  - kind: ServiceAccount
    name: test-service-account-with-generated-token
    namespace: test
```

Create these objects by using the `d8 k apply -f` command.

Enable the Kubernetes secrets engine:

```shell
stronghold secrets enable kubernetes
```

By default, the secrets engine is mounted at `kubernetes/`.
To change this behavior, pass the `-path` argument when enabling it.

Configure the mount point.
An empty configuration is allowed:

```shell
stronghold write -f kubernetes/config
```

Now configure a Stronghold role in the Kubernetes secrets engine.
This is not a Kubernetes role.
It is used to generate Kubernetes tokens for the ServiceAccount you created:

```shell
stronghold write kubernetes/roles/my-role \
  allowed_kubernetes_namespaces="*" \
  service_account_name="test-service-account-with-generated-token" \
  token_default_ttl="10m"
```

## Generate credentials

After a user authenticates to Stronghold and receives the required permissions, writing to the `creds` endpoint for a Stronghold role generates and returns a new ServiceAccount token:

```shell
stronghold write kubernetes/creds/my-role \
  kubernetes_namespace=test
```

Example output:

```console
Key                        Value
---                        -----
lease_id                   kubernetes/creds/my-role/31d771a6-...
lease_duration             10m0s
lease_renewable            false
service_account_name       test-service-account-with-generated-token
service_account_namespace  test
service_account_token      eyJHbGci0iJSUzI1NiIsImtpZCI6ImlrUEE...
```

Use the returned ServiceAccount token for authorized requests to the Kubernetes API.
Permissions are controlled by role bindings attached to the ServiceAccount:

```shell
curl -sk "$(d8 k config view --minify -o 'jsonpath={.clusters[].cluster.server}')/api/v1/namespaces/test/pods" \
  --header "Authorization: Bearer eyJHbGci0iJSUzI1Ni..."
```

Example response:

```console
{
  "kind": "PodList",
  "apiVersion": "v1",
  "metadata": {
    "resourceVersion": "1624"
  },
  "items": []
}
```

After the [lease](../../concepts/lease/) expires, verify that the token has been revoked and can no longer be used for requests to the Kubernetes API:

```shell
curl -sk "$(d8 k config view --minify -o 'jsonpath={.clusters[].cluster.server}')/api/v1/namespaces/test/pods" \
  --header "Authorization: Bearer eyJHbGci0iJSUzI1Ni..."
```

Example response:

```console
{
  "kind": "Status",
  "apiVersion": "v1",
  "metadata": {},
  "status": "Failure",
  "message": "Unauthorized",
  "reason": "Unauthorized",
  "code": 401
}
```

## Token TTL

Kubernetes ServiceAccount tokens have a time to live.
When the token expires, it is revoked automatically.

When you create or update a Stronghold role, you can define the default TTL with `token_default_ttl` and the maximum TTL with `token_max_ttl`:

```shell
stronghold write kubernetes/roles/my-role \
  allowed_kubernetes_namespaces="*" \
  service_account_name="new-service-account-with-generated-token" \
  token_default_ttl="10m" \
  token_max_ttl="2h"
```

You can also set the `ttl` value when generating a token from the `creds` endpoint.
If `ttl` is not set, the default value is used.
It cannot exceed `token_max_ttl` if that parameter is configured:

```shell
stronghold write kubernetes/creds/my-role \
  kubernetes_namespace=test \
  ttl=20m
```

Example output:

```console
Key                        Value
---                        -----
lease_id                   kubernetes/creds/my-role/31d771a6-...
lease_duration             20m0s
lease_renewable            false
service_account_name       new-service-account-with-generated-token
service_account_namespace  test
service_account_token      eyJHbGci0iJSUzI1NiIsImtpZCI6ImlrUEE...
```

To verify the lifetime of a JWT token, decode it and convert the `iat` and `exp` fields from timestamp format to a human-readable form:

```shell
echo 'eyJhbGc...' | cut -d'.' -f2 | Base64 -d | jq -r '.iat,.exp|todate'
```

Example output:

```console
2022-05-20T17:14:50Z
2022-05-20T17:34:50Z
```

## API audience

Kubernetes tokens use the JWT format and contain claims.
One of them is `aud`.
It is a string or an array of strings that identifies the intended recipients of the token.
For more details, see the [JWT audience claim specification](https://datatracker.ietf.org/doc/html/rfc7519#section-4.1.3).

When you create or update a Stronghold role, you can define default audiences with the `token_default_audiences` parameter.
If this parameter is not set, the Kubernetes cluster uses its own default audience values for ServiceAccount tokens:

```shell
stronghold write kubernetes/roles/my-role \
  allowed_kubernetes_namespaces="*" \
  service_account_name="new-service-account-with-generated-token" \
  token_default_audiences="custom-audience"
```

You can also set audiences with the `audiences` parameter when generating a token from the `creds` endpoint.
If the parameter is not set, Stronghold uses the value of `token_default_audiences`:

```shell
stronghold write kubernetes/creds/my-role \
  kubernetes_namespace=test \
  audiences="another-custom-audience"
```

Example output:

```console
Key                        Value
---                        -----
lease_id                   kubernetes/creds/my-role/SriWQf0bPZ...
lease_duration             768h
lease_renewable            false
service_account_name       new-service-account-with-generated-token
service_account_namespace  test
service_account_token      eyJHbGci0iJSUzI1NiIsImtpZCI6ImlrUEE...
```

To verify the audience of a token, decode the JWT:

```shell
echo 'eyJhbGc...' | cut -d'.' -f2 | Base64 -d
```

Example output:

```console
{"aud":["another-custom-audience"]...
```

## Automatic management of roles and ServiceAccounts {#roles-and-sa}

When you configure a Stronghold role, you can pass parameters that enable automatic creation of a ServiceAccount and RoleBinding.
If needed, Stronghold can also create the Kubernetes role itself.

If you want to use an existing Kubernetes role but create the ServiceAccount and RoleBinding automatically, set the `kubernetes_role_name` parameter:

```shell
stronghold write kubernetes/roles/auto-managed-sa-role \
  allowed_kubernetes_namespaces="test" \
  kubernetes_role_name="test-role-list-pods"
```

{{< alert level="warning" >}}
The Stronghold ServiceAccount must also have access to the resources it grants access to.
For the example above, you can run `d8 k -n test create rolebinding --role test-role-list-pods --serviceaccount=stronghold:stronghold stronghold stronghold-test-role-abilities`.
This is how Kubernetes prevents privilege escalation.
For more details, see the [Kubernetes RBAC documentation](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#privilege-escalation-prevention-and-bootstrapping).
{{< /alert >}}

After that, you can get credentials by using the automatically created ServiceAccount:

```shell
stronghold write kubernetes/creds/auto-managed-sa-role \
  kubernetes_namespace=test
```

Example output:

```console
Key                          Value
---                          -----
lease_id                     kubernetes/creds/auto-managed-sa-role/cujRLYjKZUMQk6dkHBGGWm67
lease_duration               768h
lease_renewable              false
service_account_name         v-token-auto-man-1653001548-5z6hrgsxnmzncxejztml4arz
service_account_namespace    test
service_account_token        eyJHbGci0iJSUzI1Ni...
```

Stronghold can also create a role together with the ServiceAccount and RoleBinding.
To do this, set the `generated_role_rules` parameter and pass a JSON or YAML rule set for the role to create:

```shell
stronghold write kubernetes/roles/auto-managed-sa-and-role \
  allowed_kubernetes_namespaces="test" \
  generated_role_rules='{"rules":[{"apiGroups":[""],"resources":["pods"],"verbs":["list"]}]}'
```

After that, get credentials in the same way:

```shell
stronghold write kubernetes/creds/auto-managed-sa-and-role \
  kubernetes_namespace=test
```

Example output:

```console
Key                          Value
---                          -----
lease_id                     kubernetes/creds/auto-managed-sa-and-role/pehLtegoTP8vCkcaQozUqOHf
lease_duration               768h
lease_renewable              false
service_account_name         v-token-auto-man-1653002096-4imxf3ytjh5hbyro9s1oqdo3
service_account_namespace    test
service_account_token        eyJHbGci0iJSUzI1Ni...
```
