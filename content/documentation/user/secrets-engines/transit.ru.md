Механизм секретов Transit выполняет криптографические операции с данными при передаче.
Stronghold не хранит данные, отправленные в этот механизм.
Его также можно рассматривать как «криптографию как услугу» или «шифрование как услугу».

Механизм Transit позволяет:

- шифровать и расшифровывать данные;
- подписывать данные и проверять подписи;
- вычислять хеши и HMAC;
- генерировать случайные байты.

Основной сценарий использования Transit — шифрование данных в приложениях с последующим хранением зашифрованных данных во внешнем хранилище.
Это снимает с разработчиков приложений ответственность за корректную реализацию шифрования и дешифрования и переносит её на Stronghold.

Transit поддерживает производные ключи.
Это позволяет использовать один и тот же ключ для разных целей, создавая новый ключ на основе пользовательского контекста.
В этом режиме также можно включить конвергентное шифрование, при котором одинаковые входные данные дают одинаковый шифротекст.

Генерация ключей данных позволяет процессам запрашивать высокоэнтропийный ключ заданной длины.
Такой ключ возвращается в зашифрованном виде с использованием указанного ключа.
Обычно ключ также возвращается в открытом виде для немедленного использования, но эту возможность можно отключить в соответствии с требованиями аудита.

## Управление рабочим набором

Механизм Transit поддерживает версионирование ключей.
Версии ключей старше значения `min_decryption_version` архивируются, а более новые остаются в рабочем наборе.

Это важно по двум причинам:

- для производительности — ключи из рабочего набора загружаются быстрее;
- для безопасности — можно запретить расшифровку старыми версиями ключей.

Если потребуется расшифровать данные в экстренной ситуации, значение `min_decryption_version` можно временно уменьшить.

Сейчас архив хранится в одной записи хранилища.
В некоторых бэкендах, особенно использующих Raft или Paxos для обеспечения высокой доступности (HA), частая ротация ключей может привести к тому, что размер архивной записи превысит допустимый предел.

Для сценариев с частой ротацией хорошей альтернативой может быть использование именованных ключей, привязанных к временным интервалам.
Например, можно использовать 5-минутные периоды, округлённые до ближайшего значения, кратного пяти.
Это позволяет одновременно использовать несколько ключей и детерминированно выбирать нужный ключ в любой момент времени.

## Рекомендации NIST по ротации ключей

Периодическая ротация ключей шифрования рекомендуется даже в том случае, если компрометации ключа не было.

Для ключей AES-GCM ротацию следует выполнять до достижения примерно 2<sup>32</sup> операций шифрования на одну версию ключа, в соответствии с рекомендациями NIST 800-38D.
Операторам следует оценить интенсивность использования ключа и настроить частоту ротации так, чтобы не превышать этот предел.

Например, если ключ используется примерно 40 миллионов раз в день, достаточно выполнять ротацию раз в три месяца.

## Типы ключей

Сейчас механизм секретов Transit поддерживает следующие типы ключей.
Все типы ключей также генерируют отдельные ключи HMAC.

- `aes128-gcm96` — AES-GCM с 128-битным ключом AES и 96-битным `nonce`; поддерживает шифрование, дешифрование, производные ключи и конвергентное шифрование.
- `aes256-gcm96` — AES-GCM с 256-битным ключом AES и 96-битным `nonce`; поддерживает шифрование, дешифрование, производные ключи и конвергентное шифрование; используется по умолчанию.
- `chacha20-poly1305` — ChaCha20-Poly1305 с 256-битным ключом; поддерживает шифрование, дешифрование, производные ключи и конвергентное шифрование.
- `ed25519` — Ed25519; поддерживает подпись, проверку подписи и производные ключи.
- `ecdsa-p256` — ECDSA с использованием кривой P-256; поддерживает подпись и проверку подписи.
- `ecdsa-p384` — ECDSA с использованием кривой P-384; поддерживает подпись и проверку подписи.
- `ecdsa-p521` — ECDSA с использованием кривой P-521; поддерживает подпись и проверку подписи.
- `rsa-2048` — 2048-битный ключ RSA; поддерживает шифрование, дешифрование, подпись и проверку подписи.
- `rsa-3072` — 3072-битный ключ RSA; поддерживает шифрование, дешифрование, подпись и проверку подписи.
- `rsa-4096` — 4096-битный ключ RSA; поддерживает шифрование, дешифрование, подпись и проверку подписи.
- `hmac` — HMAC; поддерживает генерацию и проверку HMAC.

{{< alert level="info" >}}
Все типы ключей поддерживают операции HMAC через использование второго случайно сгенерированного ключа, который создаётся при инициализации или ротации ключа.
Тип ключа `hmac` поддерживает только операции HMAC и ведёт себя так же, как и другие алгоритмы, в части операций HMAC, но дополнительно поддерживает импорт ключей.
По умолчанию тип ключа `hmac` использует 256-битный ключ.
{{< /alert >}}

Операции RSA используют один из следующих методов:

- OAEP — для шифрования и дешифрования, с хеш-функцией SHA-256 и MGF;
- PSS — для подписи и проверки подписи, с настраиваемой хеш-функцией, которая также используется для MGF;
- PKCS#1 v1.5 — для подписи и проверки подписи, с настраиваемой хеш-функцией.

## Конвергентное шифрование

Конвергентное шифрование — это режим, в котором один и тот же набор открытого текста и контекста всегда приводит к одному и тому же шифротексту.
Это достигается за счёт получения ключа с использованием функции вывода ключа и детерминированного получения одноразового значения `nonce`.

Поскольку эти параметры различаются для любой комбинации открытого текста и контекста в ключевом пространстве размером 2^256, риск повторного использования `nonce` практически равен нулю.

У этого подхода есть много практических применений.
Один из распространённых сценариев — хранение шифротекста в базе данных с ограниченной поддержкой поиска и запросов.
В этом случае строки с одинаковым значением конкретного поля могут быть найдены по результатам запроса.

Чтобы обеспечить возможность обновления алгоритма при необходимости, исторически поддерживались разные версии конвергентного шифрования:

- Version 1 требовала, чтобы клиент самостоятельно передавал `nonce`.
  Это обеспечивало высокую гибкость, но могло быть опасным при неправильной реализации.
  Ключи, использующие эту версию, не могут быть обновлены.
- Version 2 использовала алгоритмический подход для вычисления параметров.
  Однако этот алгоритм был уязвим к офлайн-атакам подтверждения открытого текста.
  Из-за этого злоумышленник мог выполнять перебор для расшифровки, если размер открытого текста был небольшим.
  Ключи с версией 2 можно обновить, выполнив ротацию до новой версии ключа.
  После этого существующие значения можно повторно обернуть с использованием новой версии ключа, и далее будет использоваться алгоритм версии 3.
- Version 3 использует другой алгоритм, разработанный с учётом устойчивости к офлайн-атакам подтверждения открытого текста.
  Он похож на AES-SIV тем, что использует псевдослучайную функцию (PRF) для генерации `nonce` на основе открытого текста.

## Настройка

Большинство механизмов секретов требуют предварительной настройки перед использованием.
Обычно эти действия выполняет оператор или система управления конфигурацией.

Активируйте механизм секретов Transit:

```shell
stronghold secrets enable transit
```

Пример вывода:

```console
Success! Enabled the transit secrets engine at: transit/
```

По умолчанию механизм монтируется по своему имени.
Чтобы указать другой путь, используйте аргумент `-path`.

Создайте именованный ключ шифрования:

```shell
stronghold write -f transit/keys/my-key
```

Пример вывода:

```console
Success! Data written to: transit/keys/my-key
```

Обычно каждое приложение использует собственный ключ шифрования.

## Использование

После настройки механизма и получения токена Stronghold с соответствующими разрешениями можно выполнять криптографические операции.

Зашифруйте данные с помощью эндпоинта `/encrypt` и указанного ключа.

{{< alert level="info" >}}
Все данные должны быть закодированы в Base64.
Это связано с тем, что Stronghold не требует, чтобы передаваемый `plaintext` был текстом.
Например, это может быть PDF-файл, изображение или другие бинарные данные.
Самый безопасный способ передать такие данные в JSON — использовать кодирование Base64.
{{< /alert >}}

```shell
stronghold write transit/encrypt/my-key plaintext=$(echo "my secret data" | base64)
```

Пример вывода:

```console
Key           Value
---           -----
ciphertext    vault:v1:8SDd3WHDOjf7mq69CyCqYjBXAiQQAVZRkFM13ok481zoCmHnSeDX9vyf7w==
```

Возвращаемый шифротекст начинается с префикса `vault:v1:`.
Префикс `vault` показывает, что данные зашифрованы Stronghold.
Значение `v1` указывает, что использовалась первая версия ключа.

Это важно при ротации, потому что Stronghold использует правильную версию ключа для расшифровки.

Stronghold не хранит шифротекст.
Ответственность за его хранение лежит на вызывающей стороне.
Чтобы расшифровать данные, снова передайте шифротекст в Stronghold.

{{< alert level="warning" >}}
Stronghold HTTP API ограничивает размер запроса до 32 МБ для защиты от DoS-атак.
Этот лимит можно изменить в блоке `listener` [конфигурации Stronghold](../../../install/standalone/configuration/#listener).
{{< /alert >}}

Расшифруйте данные с помощью эндпоинта `/decrypt`:

```shell
stronghold write transit/decrypt/my-key ciphertext=vault:v1:8SDd3WHDOjf7mq69CyCqYjBXAiQQAVZRkFM13ok481zoCmHnSeDX9vyf7w==
```

Пример вывода:

```console
Key          Value
---          -----
plaintext    bXkgc2VjcmV0IGRhdGEK
```

Результат представляет собой строку в Base64.
Декодируйте её, чтобы получить исходные данные:

```shell
base64 --decode <<< "bXkgc2VjcmV0IGRhdGEK"
```

Пример вывода:

```console
my secret data
```

То же самое можно сделать одной командой:

```shell
stronghold write -field=plaintext transit/decrypt/my-key ciphertext=... | base64 --decode
```

Пример вывода:

```console
my secret data
```

С помощью ACL можно ограничить доступ к механизму Transit.
Например, доверенным операторам можно разрешить управление ключами, а приложениям — только шифрование и дешифрование с нужными ключами.

Выполните ротацию базового ключа шифрования.
В результате будет сгенерирован новый ключ, который будет добавлен в связку ключей именованного ключа:

```shell
stronghold write -f transit/keys/my-key/rotate
```

Пример вывода:

```console
Success! Data written to: transit/keys/my-key/rotate
```

Во всех последующих операциях шифрования будет использоваться новый ключ.
Старые данные при этом всё ещё можно расшифровать, потому что Stronghold использует связку ключей.

Обновите уже зашифрованные данные с использованием нового ключа.
Stronghold расшифрует значение с помощью подходящей версии ключа, а затем снова зашифрует открытый текст с помощью новейшего ключа:

```shell
stronghold write transit/rewrap/my-key ciphertext=vault:v1:8SDd3WHDOjf7mq69CyCqYjBXAiQQAVZRkFM13ok481zoCmHnSeDX9vyf7w==
```

Пример вывода:

```console
Key           Value
---           -----
ciphertext    vault:v2:...
```

Этот процесс не раскрывает исходные данные.
Поэтому политика Stronghold может разрешать даже недоверенным процессам выполнять `rewrap` без доступа к самим данным.

## Импорт собственного ключа. Bring your own key (BYOK)

{{< alert level="warning" >}}
Импорт ключей нужен в тех случаях, когда необходимо перенести ключ из HSM или другой системы.
Однако безопаснее, если ключ будет сгенерирован и будет управляться внутри Stronghold.
{{< /alert >}}

Сначала получите wrapping key из Transit:

```shell
stronghold read transit/wrapping_key
```

Этот ключ будет 4096-битным публичным ключом RSA.
Далее используйте его для создания зашифрованного значения для `import`.

Ниже под целевым ключом понимается импортируемый ключ.

### HSM

Если ключ импортируется из HSM, поддерживающего PKCS#11, возможны два сценария:

- Если HSM поддерживает механизм `CKM_RSA_AES_KEY_WRAP`, используйте его для обёртывания целевого ключа с помощью wrapping key.
- Если HSM не поддерживает этот механизм, используйте два механизма.
  Сначала сгенерируйте 256-битный ключ AES.
  Затем используйте его для обёртывания целевого ключа с помощью механизма `CKM_AES_KEY_WRAP_KWP`.
  После этого оберните ключ AES wrapping key с помощью механизма `CKM_RSA_PKCS_OAEP`, используя MGF1 и одну из следующих хеш-функций: SHA-1, SHA-224, SHA-256, SHA-384 или SHA-512.

Шифротекст создаётся путём добавления обёрнутого целевого ключа к обёрнутому ключу AES.
Байты шифротекста должны быть закодированы в Base64.

### Процесс вручную

Если целевой ключ не хранится в HSM или KMS, для создания шифротекста для эндпоинта `import` выполните следующие шаги:

1. Сгенерируйте эфемерный 256-битный ключ AES.
1. Оберните целевой ключ эфемерным ключом AES с помощью AES-KWP.
1. Оберните ключ AES в wrapping key Stronghold с помощью RSAES-OAEP с MGF1 и одной из следующих хеш-функций: SHA-1, SHA-224, SHA-256, SHA-384 или SHA-512.
1. Удалите эфемерный ключ AES.
1. Добавьте обёрнутый целевой ключ к обёрнутому ключу AES.
1. Закодируйте результат в Base64.

{{< alert level="warning" >}}
При обёртывании симметричного ключа, например ключа AES или ChaCha20, оборачивайте необработанные байты ключа.
Например, для 128-битного ключа AES это будет массив длиной 16 байт, который нужно обернуть без Base64 и других кодировок.

При обёртывании асимметричного ключа, например ключа RSA или ECDSA, оборачивайте ключ в формате PKCS8 в сырой DER-бинарной форме.
Не применяйте PEM-кодировку перед шифрованием и не кодируйте ключ в Base64.
{{< /alert >}}
