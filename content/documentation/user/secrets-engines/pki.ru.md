Механизм секретов PKI позволяет Stronghold работать как центр сертификации (CA).
Он может генерировать динамические корневые и промежуточные сертификаты, а также подписывать сертификаты по запросу.

Механизм секретов инфраструктуры открытых ключей (Public Key Infrastructure, PKI) генерирует динамические сертификаты X.509.
С его помощью сервисы получают сертификаты без ручного создания закрытого ключа и CSR, отправки запроса в CA и ожидания проверки и подписи.
Встроенные механизмы аутентификации и авторизации Stronghold обеспечивают необходимую проверку.

Если использовать короткий TTL, необходимость отзыва сертификатов возникает реже.
Это позволяет поддерживать короткий список отзыва сертификатов (certificate revocation list, CRL) и снижает нагрузку на механизм секретов.
Благодаря этому каждый экземпляр приложения может использовать собственный сертификат без совместного использования и связанных с этим проблем ротации и отзыва.

Кроме того, механизм секретов PKI позволяет использовать эфемерные сертификаты.
Их можно получать и хранить в памяти при запуске приложения, а затем удалять при завершении работы, не записывая на диск.

## Настройка

Большинство механизмов секретов нужно настраивать заранее, чтобы они могли выполнять свои функции.
Обычно эти действия выполняет оператор или система управления конфигурацией.

1. Включите механизм секретов PKI:

   ```shell
   d8 stronghold secrets enable pki
   ```

   Пример вывода:

   ```console
   Success! Enabled the pki secrets engine at: pki/
   ```

   По умолчанию механизм секретов монтируется по имени движка.
   Чтобы включить его по другому пути, используйте аргумент `-path`.

1. Увеличьте TTL механизма секретов.
   Значение по умолчанию, равное 30 дням, может быть слишком маленьким.
   Например, можно увеличить его до одного года:

   ```shell
   d8 stronghold secrets tune -max-lease-ttl=8760h pki
   ```

   Пример вывода:

   ```console
   Success! Tuned the secrets engine at: pki/
   ```

   Отдельные роли могут дополнительно ограничивать это значение для конкретных сертификатов.
   Этот параметр задаёт только глобальный максимальный TTL для механизма секретов.

1. Настройте сертификат CA и закрытый ключ.
   Stronghold может использовать существующую пару ключей или сгенерировать собственный самоподписанный корневой сертификат.
   Обычно корневой CA рекомендуется хранить вне Stronghold, а в Stronghold загружать подписанный промежуточный CA.

   ```shell
   d8 stronghold write pki/root/generate/internal \
     common_name=my-website.ru \
     ttl=8760h
   ```

   Пример вывода:

   ```console
   Key              Value
   ---              -----
   certificate      -----BEGIN CERTIFICATE-----...
   expiration       1756317679
   issuing_ca       -----BEGIN CERTIFICATE-----...
   serial_number    fc:f1:fb:2c:6d:4d:99:1e:82:1b:08:0a:81:ed:61:3e:1d:fa:f5:29
   ```

   Возвращаемый сертификат используется только для информации.
   Закрытый ключ безопасно хранится внутри Stronghold.

1. Обновите URL для CRL и выпускающих сертификатов.
   При необходимости эти значения можно изменить позже:

   ```shell
   d8 stronghold write pki/config/urls \
     issuing_certificates="http://127.0.0.1:8200/v1/pki/ca" \
     crl_distribution_points="http://127.0.0.1:8200/v1/pki/crl"
   ```

   Пример вывода:

   ```console
   Success! Data written to: pki/config/urls
   ```

1. Настройте роль, которая сопоставляет имя роли в Stronghold с правилами генерации сертификатов.
   Когда пользователи или машины запрашивают учётные данные, сертификаты выпускаются в рамках этой роли:

   ```shell
   d8 stronghold write pki/roles/example-dot-ru \
     allowed_domains=my-website.ru \
     allow_subdomains=true \
     max_ttl=72h
   ```

   Пример вывода:

   ```console
   Success! Data written to: pki/roles/example-dot-ru
   ```

## Использование

После настройки механизма секретов и получения Stronghold-токена с нужными правами можно генерировать учётные данные.

1. Сгенерируйте новые учётные данные, записав запрос в путь `/issue` с именем роли:

   ```shell
   d8 stronghold write pki/issue/example-dot-ru \
     common_name=www.my-website.ru
   ```

   Пример вывода:

   ```console
   Key                 Value
   ---                 -----
   certificate         -----BEGIN CERTIFICATE-----...
   issuing_ca          -----BEGIN CERTIFICATE-----...
   private_key         -----BEGIN RSA PRIVATE KEY-----...
   private_key_type    rsa
   serial_number       1d:2e:c6:06:45:18:60:0e:23:d6:c5:17:43:c0:fe:46:ed:d1:50:be
   ```

   В ответе возвращаются динамически сгенерированные закрытый ключ и сертификат.
   Сертификат соответствует указанной роли и истекает через 72 часа, как задано в конфигурации роли.
   Также возвращаются выпускающий CA и цепочка доверия, чтобы упростить автоматизацию.
