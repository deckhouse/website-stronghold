Identity information is used throughout Stronghold, but it can also be exported
for use by other applications. An authorized user or application can request a token
that contains identity information for the associated entity. These tokens are signed JWTs
that conform to the structure of an [OIDC ID token](https://openid.net/specs/openid-connect-core-1_0.html#IDToken).

The public keys used to authenticate tokens are published by Stronghold at an
unauthenticated endpoint in accordance with the OIDC discovery and JWKS conventions,
which should be consumed directly by JWT/OIDC libraries. Stronghold also provides
an introspection endpoint for token validation.

## Roles and keys

OIDC-compliant ID tokens are generated based on a role, which allows you to configure
token requirements using a templating system, the token TTL, and the key to use
for signing the token. The role template is an optional parameter used to configure
the token contents and is described in the next section. The token TTL controls
how long the token remains valid, after which validation libraries will treat it
as invalid. Every role has an associated `client_id`, which is added to the token's
`aud` claim. JWT/OIDC libraries usually require this value. The parameter can be set
by the operator to any selected value, or, if it is not set, a value generated
by Stronghold will be used.

The role's `key` parameter binds the role to an existing named key. Multiple roles
can reference the same key. It is not possible to generate an unsigned ID token.

A named key is a public/private key pair generated by Stronghold. The private key
is used to sign identity tokens, and the public key is used by clients to verify
the signature. Keys are rotated regularly. When rotation occurs, a new key pair
is generated, and the previous public key is retained for a limited time
for validation.

The named key configuration specifies the rotation period, validation TTL,
signing algorithm, and allowed client IDs. The rotation period determines
how often a new signing key is generated and the private part of the previous
signing key is removed. The validation TTL is the period during which the public key
is retained for validation after rotation. By default, keys are rotated
every 24 hours and remain available for validation for 24 hours after
rotation.

The key's list of allowed client IDs restricts which roles can reference that key.
This parameter can be set to `*` to allow all roles. Validity is evaluated
when a token is requested, not during configuration.

## Token contents and templates

Identity tokens always contain, at a minimum, the required OIDC claims:

- `iss` — issuer URL;
- `sub` — requesting entity ID;
- `aud` — the role's `client_id`;
- `iat` — issue time;
- `exp` — token expiration time.

In addition, the operator can configure templates for each role to add
various entity information to the token. Templates are structured as JSON
with replaceable parameters. The parameter syntax is the same as that used
for [ACL Path Templating](../../../concepts/policy/).

For example:

```json
{
  "color": {{identity.entity.metadata.color}},
  "userinfo": {
     "username": {{identity.entity.aliases.usermap_123.metadata.username}},
     "groups": {{identity.entity.groups.names}}
  },
  "nbf": {{time.now}}
}
```

When a token is requested, the resulting template can be rendered as follows:

```json
{
  "color": "green",
  "userinfo": {
     "username": "bob",
     "groups": ["web", "engr", "default"]
  },
  "nbf": 1561411915
}
```

This content is then merged with the base OIDC claims into the final token:

```json
{
  "iss": "https://10.1.1.45:8200/v1/identity/oidc",
  "sub": "a2cd63d3-5364-406f-980e-8d71bb0692f5",
  "aud": "SxSouteCYPBoaTFy94hFghmekos",
  "iat": 1561411915,
  "exp": 1561412215,
  "color": "green",
  "userinfo": {
    "username": "bob",
    "groups": ["web", "engr", "default"]
  },
  "nbf": 1561411915
}
```

Note how template merging works: top-level template keys become top-level token keys.
For this reason, templates cannot contain top-level keys that override
standard OIDC claims.

Template parameters that are missing for the entity, such as nonexistent metadata
or a nonexistent alias accessor, are rendered as empty strings or empty objects,
depending on the data type.

Templates are configured per role and can additionally be encoded in Base64 [1].

The full list of template parameters is shown below:

| Name | Description |
| --- | --- |
| `identity.entity.id` | Entity ID |
| `identity.entity.name` | Entity name |
| `identity.entity.groups.ids` | IDs of groups the entity is a member of |
| `identity.entity.groups.names` | Names of groups the entity is a member of |
| `identity.entity.metadata` | Metadata associated with the entity |
| `identity.entity.metadata.<metadata key>` | Entity metadata for the specified key |
| `identity.entity.aliases.<mount accessor>.id` | Entity alias ID for the specified mount |
| `identity.entity.aliases.<mount accessor>.name` | Entity alias name for the specified mount |
| `identity.entity.aliases.<mount accessor>.metadata` | Metadata associated with the alias for the specified mount |
| `identity.entity.aliases.<mount accessor>.metadata.<metadata key>` | Alias metadata for the specified mount and metadata key |
| `identity.entity.aliases.<mount accessor>.custom_metadata` | Custom metadata associated with the alias for the specified mount |
| `identity.entity.aliases.<mount accessor>.custom_metadata.<custom_metadata key>` | Alias custom metadata for the specified mount and custom metadata key |
| `time.now` | Current time in whole seconds since the epoch |
| `time.now.plus.<duration>` | Current time plus `duration` |
| `time.now.minus.<duration>` | Current time minus `duration` |

## Token generation

An authenticated client can request a token using the token generation
endpoint. The token is generated according to the requested role's specifications
for the requesting entity. It is not possible to generate a token
for an arbitrary entity.

## Validating identity tokens generated by Stronghold

An identity token can be validated on the client side using the public keys
published by Stronghold, or through the introspection endpoint provided
by Stronghold.

Stronghold serves standard [.well-known](https://tools.ietf.org/html/rfc5785)
endpoints that make integration with OIDC validation libraries straightforward.
Library configuration usually requires providing the issuer URL and
the client ID. The library then handles key retrieval and validates
token signatures and claims. The advantage of this approach is that it requires
only _access_ to Stronghold, not _authorization_, because `.well-known`
endpoints are unauthenticated.

Alternatively, the token can be sent to Stronghold for validation through
the `introspection endpoint`.
The response indicates whether the token is active and includes any
validation errors. In addition to allowing the client to delegate validation
to Stronghold, this endpoint also performs an extra check to determine
whether the entity is still active, which cannot be determined from the token
alone. Unlike the `.well-known` endpoint, access to the introspection endpoint
requires a valid Stronghold token and sufficient authorization.

## Issuer considerations

The identity token system has one configurable parameter: the issuer.
The `iss` claim is especially important for proper token validation
by clients. Token consumers retrieve public keys from Stronghold using
the issuer URL, so that URL must be reachable over the network. In addition,
the returned key set includes the issuer, which must match the request.

By default, Stronghold sets the issuer to the Stronghold instance address
specified in [`api_addr`](../../../../install/standalone/configuration/#параметры-высокой-доступности).
This means that tokens issued in a given cluster must be validated within
that cluster. Alternatively, the `issuer` parameter can be set explicitly.
This address must point to the `identity/oidc` path of the Stronghold instance
(for example, `https://stronghold.example.com:8200/v1/identity/oidc`) and must be
reachable by any client attempting to validate identity tokens.
